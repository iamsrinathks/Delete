**What the screenshots show**
- **`/sandbox policy`** now has a **Host filter: local proxy** section:
  - `Allow: github.com`, which you set.
  - `Allow: localhost`, `127.0.0.1` and `::1`, which **the CLI adds automatically**.
  - So **loopback is always allowed** once you set an allowlist. That fits the NW-08 finding: on Windows, commands need loopback to reach the proxy.
- **Session ON:**
  - `git ls-remote github.com` → ✅ exit 0.
  - `curl github.com` with the certificate workaround → ✅ **HTTP 200**.
  - `curl pypi.org` → ⛔ **"CONNECT tunnel failed, response 403"**, with the CLI note *"sandbox is active and blocked this command's network access"*.
  - pypi.org returned **200 in Session OFF**, so this **block comes from the sandbox allowlist**. Pass ✅
- **Python check: invalid test, not a network result.**
  - `python.exe` → *"The file cannot be accessed by the system"*.
  - Most likely `python` is only the **Microsoft Store alias** (`WindowsApps\python.exe`), and the sandbox can't open it. To confirm, run in the **test window**: `Get-Command python | Select-Object Source`.
  - If the path contains `WindowsApps`, add it to the FAQ: *"Store Python aliases don't run in the sandbox. Install Python properly."*
- **Session OFF host checks:**
  - `api.github.com` → **200** ✅, usable.
  - `test.pypi.org` and `1.1.1.1` → **connection reset by the corporate filter** ❌, so not usable.
