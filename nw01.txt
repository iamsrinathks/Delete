**2. The HTTPS failure is a certificate problem only, and curl has a workaround.**
- `Test-Path $env:CURL_CA_BUNDLE` → **True**. Read in the **same command**, the CA file exists.
  - The earlier "does not exist" error happened because the path changes on each command. Each shell call gets a **new temporary CA file**, and the old one is deleted.
- With `--cacert $env:CURL_CA_BUNDLE`, the **certificate chain is accepted**. The new error is ***"the revocation status is unknown"***.
  - Schannel checks whether the certificate has been revoked. The proxy's own certificate has no revocation URL it can reach, so the check fails.
- **The likely fix is to add `--ssl-no-revoke`.** Please test it in Session ON with the SHELL prompt:

  ```powershell
  curl.exe -sS -o NUL -w "HTTP %{http_code}" --max-time 15 --cacert $env:CURL_CA_BUNDLE --ssl-no-revoke https://github.com
  ```
  - `HTTP 200` means confirmed.

**3. PowerShell `Invoke-WebRequest` has no workaround.**
- With `-Proxy $env:HTTPS_PROXY`, the request **reaches the proxy** (no more "Unable to connect"). Then it fails with ***"Could not establish trust relationship for the SSL/TLS secure channel"***.
- PowerShell 5.1 trusts **only the Windows certificate store**, and the Copilot CA isn't in it.

> ⚠️ **Do not fix this by importing the `copilot-credential-ca` file into the Windows certificate store.** Every program on the device, outside the sandbox too, would then trust certificates signed by that CA. That's a **TLS interception risk** for InfoSec. Put this in the user FAQ as a **"never do"**.
