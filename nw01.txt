**NW-08 (local network OFF)** gave a clear and important result: on Windows, `allowLocalNetwork: false` **stops every sandboxed command from starting**, not just local traffic.

**What happened**
- **`/sandbox policy`** shows **Outbound: allowed** and **Local network: blocked**, so the setting was applied.
- **curl to localhost** → the command **didn't start**: *"Cannot start sandboxed command: Sandboxed commands cannot reach the local proxy because local network access is disabled"*.
- **curl to the gateway, 172.17.16.1** → the **same error**. The command didn't start.
- **Server window** → **no new lines after 12:29**. Nothing reached it. The 12:29 lines were your Session OFF runs.
- **Web fetch to localhost** → *"Sandbox blocks local network access."* So the **fetch tool follows the local-network setting**, which is NW-13 passing.
- The **`172.17.16.1` "command" that was aborted** didn't count. The IP address was sent as a command on its own and you cancelled the approval prompt. You don't need to redo it.

**What it means**
- On Windows, **every sandboxed command goes through the built-in proxy on 127.0.0.1**. Turning local network off cuts commands off from that proxy, so nothing runs: not git, not npm, nothing.
- The plan expected this only for **NW-10** (host rules set **and** local network off). It actually happens **even with no host rules**.
- **Fleet policy decision:** on Windows, **`allowLocalNetwork` must stay `true`**. There's no way to isolate local-network traffic.
  - Example: a developer's local Postgres on `localhost:5432` stays reachable from the sandbox for any proxy-aware tool. **InfoSec needs to accept this** as a known gap in place of NW-04, which is now closed.
- **NW-10 is effectively proven.** You can still run it later for completeness: it needs one key change plus one command.
