Speaker Notes (2 Minutes):
"Good [morning/afternoon]. Today we are going to talk about the Model Context Protocol, or MCP.

We are currently in a transition period in AI development. We’ve moved past just chatting with bots; we are now trying to build agents that do real work. But there is a massive friction point: Interoperability.

MCP is an open standard—originally open-sourced by Anthropic but now an industry-wide initiative—that standardizes how AI models interact with external data and tools.

Think of MCP as the USB-C port for AI.
Before USB-C, you needed a different cable for your printer, your mouse, and your monitor. It was messy. MCP does for AI what USB did for hardware. It provides a universal way for any AI application (like Claude or an IDE) to connect to any data source (like Google Drive, Slack, or PostgreSQL) without custom integrations."

Slide 2: The "Brain in a Jar" Problem

Visual: An illustration of a glowing brain floating inside a glass jar, isolated. Outside the jar are icons for Databases, Logs, and Code Repositories.

Speaker Notes (2 Minutes):
"To understand why we need MCP, we have to look at the fundamental limitation of Large Language Models today.

I call this the 'Brain in a Jar' problem.
LLMs are geniuses. They know everything about Python syntax, history, and literature. But they are locked in a room.

They don't know about the production outage that started 10 minutes ago.

They can't see the private code in your GitHub repository.

They can't query your customer database.

Currently, to get data into the brain, we either copy-paste logs manually (which is insecure and slow) or we try to build custom bridges. But the model remains fundamentally isolated from the context it needs to solve your specific business problems."

Slide 3: The N x M Problem

Visual: A chaotic web of lines.

Left side: 5 different AI Models (Claude, GPT-4, Llama, Gemini, Mistral).

Right side: 5 different Data Sources (Slack, Jira, SQL, Local Files, Splunk).

Middle: A mess of crisscrossing lines connecting everything to everything.

Speaker Notes (2 Minutes):
"This isolation forces developers to build custom integrations. And that leads us to the N-by-M Problem.

If you have 5 different AI tools you want to use (like Cursor, Claude, and ChatGPT) and 5 different data sources (like Jira, GitHub, and SQL), you theoretically have to build and maintain 25 different integrations.

If OpenAI changes their API? You rewrite code.

If you migrate from Jira to Linear? You rewrite code.

This is 'Spaghetti Integration.' It is fragile, it doesn't scale, and it is a nightmare to secure. We are spending more time maintaining pipelines than building actual AI agents. MCP solves this by placing a standard protocol in the middle. You build the connector once, and it works for every model."

Slide 4: Architecture of MCP

Visual: A clean architectural diagram (based on official docs).

Host (Left): The Application (e.g., VS Code, Claude Desktop).

Client (Inside Host): The MCP Client (maintains the connection).

Transport Layer: Arrows labeled "Stdio" (Local) and "SSE" (Remote/HTTP).

Server (Right): The MCP Server (The gateway to data).

Primitives: Icons for Resources (Data), Prompts (Templates), Tools (Functions).

Speaker Notes (3 Minutes):
"So, how does it work under the hood? The architecture is client-server based.

The Host: This is the AI application you are using, like VS Code or the Claude Desktop app.

The Client: Inside the host, there is an MCP Client. Its job is to maintain a 1:1 connection with the server.

The Server: This is the most important part for us. The MCP Server is a lightweight program that sits on top of your data. It exposes three specific things:

Resources: Passive data like reading a log file.

Prompts: Pre-written templates for common tasks.

Tools: Executable functions, like 'run_query' or 'restart_pod.'

The Transport:

If you are running locally, they talk via Stdio (standard input/output).

If you are running in an enterprise architecture (like the Cloud Run model we discussed previously), they talk via SSE (Server-Sent Events) over HTTP.

The beauty here is that the Host doesn't know how to query the database. It just asks the Server, 'What tools do you have?' and the Server replies, 'I can run SQL.' The protocol handles the rest."

Slide 5: Security & Risks

Visual: A "Warning" slide listing the Top 5 Risks.

Unauthorized Tool Exposure

Session Hijacking

Tool Shadowing

Sensitive Data Exposure

Authentication Bypass

Speaker Notes (3 Minutes):
"However, connecting our internal data to AI agents introduces new attack vectors. We need to be aware of the top five MCP deployment risks:

Unauthorized Tool Exposure: If we misconfigure the MCP manifest, we might accidentally give an AI agent 'Admin' rights when it should only have 'Read' rights. We must apply the Principle of Least Privilege to tool definitions.

Session Hijacking: Since MCP often uses persistent connections (especially over SSE), if an attacker steals a session ID, they can impersonate a user and inject malicious commands into the data queue.

Tool Shadowing: This is like phishing. A malicious actor could deploy a rogue MCP server that looks like a legitimate internal tool to trick an agent into sending it sensitive data.

Sensitive Data Exposure: We must ensure that our MCP servers don't leak API keys or PII (Personally Identifiable Information) into the context window of the LLM, where it could be stored or leaked later.

Authentication Bypass: If we deploy MCP servers as web services, we must enforce strict authentication (like OIDC). Without it, attackers could bypass the AI entirely and hit the API directly.

Security must be baked into the MCP server, not just the AI agent."

The MCP Server securely queries the Google Cloud API using my credentials.

The logs are returned directly into the chat window.

Copilot then analyzes those logs and suggests a fix—all without me ever leaving the IDE. This is the power of context.
