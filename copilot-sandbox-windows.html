Copilot Local Sandboxing on Windows 11: How It Works

This page explains the rollout runbook for about 700 developers on Windows 11 only. Linux, WSL2 and macOS are left out for now. Pick a scenario below. The diagram shows the path.

The idea in three points

1. Isolate the agent

The sandbox wraps each process that the Copilot agent starts. This includes shell commands and local MCP servers. It limits files, network, and credentials.

2. Push policy from three places

Intune, the .github-private repo, and a managed file in %ProgramFiles% can all send settings. For the sandbox key, Copilot combines every source and the most restrictive value wins.

3. Roll out in rings

The team starts in observe mode on Windows. Ring 0 records what the sandbox blocks and allows it. Ring 1 already blocks and records. Ring 3 removes the bypass.

    Documentation

    Deliver policy

    • Intune writes sandbox.* values to the registry.
    • Intune targets device groups. These match the rings.
    • The .github-private repo holds org-wide keys.
    • A managed file in %ProgramFiles%\GitHubCopilot is a second device channel. It loads at client start.
    • Most keys follow MDM, then server, then file, then user. The sandbox key is combined from all layers, and the most restrictive value wins.
    • For sandbox, a looser layer cannot undo a stricter layer.

    Before you start

    • Update Windows. 25H2 needs KB5124010 (build 26200.9550) or later. 26H1 needs KB5124006 or later.
    • GitHub's prerequisite does not name 24H2. Check Microsoft's support matrix before you include it.
    • Upgrade clients first: VS Code 1.141.0, CLI 1.0.93, app 1.1.26. Audit pinned VDI images before any sandbox key is assigned. Older clients lose Copilot.
    • Put the baseline (enabled, failIfUnavailable, allowBypass, forceRemoteSettingsRefresh) in Intune and the file, so it applies before sign-in. Use server team overrides only for specialisation. They wrap the whole sandbox object in overridable, and the most-restrictive rule still applies.
    • Create the ring teams. Test any exempt-team override first. Team overrides work for server-managed settings only, and sandbox support is only partly documented.

    Key settings

    • sandbox.enabled forces the sandbox on.
    • learningMode sets allow or deny. It works on Windows only. allow is accepted only through Intune or the registry, not the file.
    • failIfUnavailable, with enabled, blocks model and tool execution when the sandbox cannot be enforced.
    • allowBypass controls the one-off bypass prompt. false also blocks /sandbox disable in the CLI.
    • userPolicy.network.allowedHosts lists the hosts a command may reach. Outbound stays open until a list is set.
    • Keep addCurrentWorkingDirectory on. Turning it off removes access to .git, so git status, add, commit and diff fail unless you grant .git by hand.
    • On Windows, keep allowLocalNetwork on when host rules, an upstream proxy or credential masking are used. Sandboxed processes reach the CLI's local proxy over loopback.
    • forceRemoteSettingsRefresh requires a fresh policy at startup and fails closed. VS Code blocks Copilot. The CLI limits MCP servers and bypass mode until a fetch works.

    Known risks

    • Old clients lose Copilot when the sandbox key arrives.
    • Windows host rules are soft. The corporate proxy is the real control.
    • Built-in file tools run outside the sandbox.
    • Observe with telemetry too. Set managed telemetry with capture.identity and policyDetail to true. policyDetail exports raw sandbox filesystem paths, so turn it off once the allow-lists are settled.
    • Remote MCP servers run outside the sandbox.
    • An allowed host can still carry data out.
    • Model refusals are not a control.
